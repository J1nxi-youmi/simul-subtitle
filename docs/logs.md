# 使用记录与调试

## 会话使用记录（JSONL）

使用记录**默认关闭**。在「设置 → 使用记录」中打开「记录每次使用」后，从下一次开始字幕起，每次会话都会在本地生成一份 `.jsonl` 日志文件；关闭开关后不再生成新文件，已有记录会保留在本地，可随时在设置页分享或删除。

### 三端保存位置

| 平台 | 日志目录路径 | 文件命名格式 |
|---|---|---|
| **Android** | `Android/data/io.github.korenkrita.simulsub/files/logs/` | `session-YYYYMMDD-HHMMSS.jsonl` |
| **Windows** | `%APPDATA%\SimulSub\logs\` | `session-YYYYMMDD-HHMMSS.jsonl` |

### 写入与安全机制

- **后台异步写入**：日志在独立后台线程写入，不会阻塞识别、翻译或界面渲染。
- **`.part` 原子转正**：会话进行期间文件名以 `.part` 结尾，仅当会话正常结束时才重命名为正式的 `.jsonl` 文件，避免异常中断的残缺文件被当作完整记录。
- **严格脱敏**：日志文件本身**不包含音频数据**，也**不包含任何 API Key、自定义请求头的值**，且不记录翻译服务端返回的原始流式响应报文或思考过程。开启「同时保留音频」后，音频以**单独的 `.wav` 文件**与日志保存在同一目录（见下文「会话音频」），日志与音频互不混写。

### JSONL 事件格式

文件每行是一个独立的 JSON 对象，公共字段 `ev` 表示事件类型，`t` 表示单调时钟毫秒数（monotonic ms）：

| 事件类型（`ev`） | 记录时机与包含字段 |
|---|---|
| `session_start` | 会话启动时记录：当前场景、源语言与目标语言、Jev 开关、上文参考句数等；桌面端额外记录 `proxy`（翻译请求所走的代理/直连路由） |
| `byok` | 记录当前生效的翻译服务配置：服务地址、模型 ID、关闭思考所用的参数、自定义 `User-Agent` 及自定义请求头的**名称列表**（不含 Key 与请求头的值） |
| `byok_probe` | 首次使用某套「地址 + 模型」时，记录关闭思考参数的探测过程与结果 |
| `config_change` | 字幕运行期间修改设置时写入：生成新的配置编号 `setup`，后续每条翻译记录中的 `setup` 字段均指向其实际使用的配置编号 |
| `audio_start`（开启「同时保留音频」后） | 本会话第一帧音频到达时写入：`file`（WAV 文件名，与日志同名）、`t0`（文件第 0 个采样点对应的单调时钟毫秒数）、`hal`（时间戳是否来自系统音频硬件时钟）。用于把音频和各事件按时间对齐，见下文 |
| `sysaudio`（仅桌面端） | 记录音频采集子进程绑定的播放设备名称，以及每 5 秒一次的音频采样与音量统计 |
| 识别 / 翻译 / Jev / 上屏事件 | 记录每次本地语音识别结果、每次翻译请求的完整提示词、剥离思考内容与 Key 后的译文、HTTP 状态码、各阶段耗时、`usage`（含服务端回报的 `cached_tokens`）、每次 Jev 请求与原始判断结果，以及最终显示在悬浮窗上的每条字幕 |

## 会话音频（可选 WAV）

纯文本日志无法追溯识别错字——模型听错的内容在文本里并不存在。因此设置里新增了「同时保留音频」（默认关闭，且需要「记录每次使用」已开启）：打开后，每次会话会把采集到的声音原样存成一份 WAV 文件，与日志同目录、同一个文件名主干（`session-20261023-214100.jsonl` 对应 `session-20261023-214100.wav`），方便对着音频回放核对每条字幕。

### 文件格式与完成语义

- **格式**：16 kHz、单声道、16-bit PCM WAV，与采集完全一致，不做压缩或转码。
- **`.part` 语义**：录音进行中写成 `….wav.part`（WAV 头的两个长度字段先留空）；只有会话正常结束时才回填这两个长度字段并重命名为 `.wav`。写失败、队列积压或异常中断的录音**永远保留 `.part` 后缀**，不会被误当成完整记录。
- **体积上限**：每次开始录音前，自动删除同目录**最旧的完整 `.wav`**，使 WAV 总量不超过 200 MB；`.wav.part` 永不自动清理。
- **失败不影响字幕**：写盘在独立后台线程完成，采集线程只把帧放进一个有界队列、从不等待。队列满或写失败时，本次录音停止并在悬浮窗提示「⚠ 音频写入失败，本次录音不完整」，字幕会话照常进行——音频不是主链路。
- **隐私**：音频只保存在本地，与日志一样不上传；不开启这个开关就不会产生任何音频文件。

### `audio_start` 事件与时间对齐

开启音频后，日志在本会话第一帧音频到达时写入一条 `audio_start`：

| 字段 | 含义 |
|---|---|
| `file` | 本会话的 WAV 文件名（与 JSONL 同名，后缀 `.wav`） |
| `t0` | WAV 文件**第 0 个采样点**对应的单调时钟毫秒数（与各事件的 `t` 同一时钟） |
| `hal` | `t0` 是否来自音频硬件（HAL）采集时间戳；为 `false` 时是读取时间，对齐精度略差 |

**对齐公式：WAV 文件第 n 个采样点 ≈ `t0` + n / 16（毫秒）**（16 kHz 即每 16 个采样点 1 毫秒）。例如 `t0 = 51320` 时，第 16000 个采样点约在 `51320 + 1000 = 52320 ms`。把某条字幕事件的 `t` 与这句话起止采样点的对齐时间相减，就能在音频里定位那段话。

## Android `logcat` 性能与延迟指标

在 Android 上连接 `adb` 可实时查看每条字幕在流水线各阶段的耗时（`logcat` 仅输出字数与耗时统计，**不输出原文和译文内容**）：

```bash
adb logcat -s jpsub
# seg=3.4F audio=3072 wait=319 asrQ=9 asr=35 mtQ=13 mt=225 mtDone=601 ja=18 zh=12
# shown seg=3.4F update=640ms hal=true
```

| 字段 | 含义 |
|---|---|
| `seg=段.版本F/d` | 句子段号与内部版本号；`F` = 定稿（Final），`d` = 草稿（Draft） |
| `audio` | 该段语音的音频时长（ms） |
| `wait` | 从最后一个有效语音采样到分句器判定说完所等待的时间（ms） |
| `asrQ` / `asr` | 识别线程排队耗时 / 离线语音识别解码耗时（ms） |
| `mtQ` / `mt` | 翻译线程排队耗时 / 翻译网络请求耗时（ms） |
| `mtDone` | 从最后一个音频采样到翻译完成的总耗时（ms） |
| `update` | 从最后一个音频采样到悬浮窗文本更新上屏的总耗时（ms，指视图更新时刻而非硬件显示帧） |
| `hal` | 是否采用 `AudioRecord` 硬件时间戳；为 `false` 时回退为读取时间，耗时数字前会带 `~` 且数值偏小 |
| `ja` / `zh` | 原文 / 译文的字符数 |

> 在 App「设置 → 字幕」中打开「显示识别和翻译用时」后，这些耗时指标也会直接显示在悬浮字幕下方。
